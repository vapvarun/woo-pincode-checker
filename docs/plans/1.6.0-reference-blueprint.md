# Blueprint: building a plugin in the mould of woo-custom-my-account-page (WCMP) 1.7.0

Reference root = `.../scratchpad/woo-custom-my-account-page/` (paths below are relative to it).
Target = `pincode-checker-for-woocommerce` 1.6.0, text domain `woo-pincode-checker`.
Suggested prefix: **`wcpc`** (functions/options/hooks/CSS/JS handles/DOM ids `wcpc_*`/`wcpc-*`), constants `WCPC_*`, classes `Woo_Pincode_Checker_*` (mirrors WCMP's `wcmp_` + `Woo_Custom_My_Account_Page_`). Verify `wcpc` does not collide with the 1.5.x plugin's own options/hooks before committing to it (1.6.0 is a rewrite; keep old option names readable for migration, see 4).

### 1.3 Autoloading
None. No composer autoload, no PSR-4. Boilerplate `load_dependencies()` does 3 `require_once` (`includes/class-woo-custom-my-account-page.php:102-120`). WordPress Plugin Boilerplate shape. Hooks are registered in the core class's `define_admin_hooks()` / `define_public_hooks()` (`:129-174`) instead of via a loader class (CLAUDE.md:267), the god class `..._Functions` registers its own hooks in its constructor (`functions:74-111`) and self-instantiates at file load (`functions:1229-1233`) - which is why `plugins_loaded` ordering matters.

For 1.6.0 (rewrite): keep the boilerplate file naming (`includes/`, `admin/`, `public/`) since the manifest/QA tooling and `.distignore` assume it, but do NOT copy the god class; give each concern a small class (see 4, 6) and a tiny classmap/`require_once` list in the core class. A PSR-4 composer autoloader is allowed by the skill (`wp-plugin-development`), but then the zip must ship `vendor/autoload.php` and `build-release.sh` Gate 5 (`REQUIRED=...`) needs it asserted.

### 1.4 Init sequence (hook order, all verified in source)
`plugins_loaded -9999`? no: `plugins_loaded -999` lib loader picks newest `Wbcom_Settings_Page` (`loader.php:49`) -> `plugins_loaded` 10 `wcmp_plugins_files` -> core ctor (loads files, locale, hooks) -> `init` **0** `wcmp_update_old_items` (legacy migration, functions:107) -> `init` **1** `boot_settings_page` (`Wbcom_Settings_Page::boot` + nav filter + tab action, includes:135) -> `init` 20 `register_block` -> `init` 21 `wcmp_add_custom_endpoints` (rewrite endpoints) -> `init` 30 `wcmp_maybe_flush_rewrite_rules` (transient flush) -> `init` 100 `Functions::init` (builds menu). `admin_menu` 5 parent menu, 20 shell child. `load_plugin_textdomain` on `init` (default prio) for WP 6.7+ (`includes:78-89`) - note it runs AFTER `init` prio 1 `boot_settings_page`, so labels passed to `boot()` at prio 1 are translated before the domain is loaded unless the domain is JIT-loaded (WP 6.7 JIT works for wordpress.org/ bundled `languages/` only when slug-named). For 1.6.0: load the textdomain at `init` prio 0 or earlier than `boot_settings_page`.

### 1.5 `lib/wbcom-settings/` - the shared library
- Five files (loader 72 lines, class 599, settings.css 1095, settings-rtl.css 1025, settings.js 69). Not Composer, not a submodule: **copy-vendored into every plugin**, intentionally (`loader.php:3-13`; same model as Action Scheduler / EDD SDK).
- Versioning: each plugin calls `wbcom_settings_register( $version, $classfile )` into global `$wbcom_settings_copies` (`loader.php:35-51`); `plugins_loaded -999` `wbcom_settings_load()` `uasort(version_compare)`, `array_key_last` -> `require_once` only the newest, only if `Wbcom_Settings_Page` is not yet defined (`:58-71`). Because the class is loaded from ONE plugin's directory, `assets_url` per page (`boot()['assets_url']`) tells it where to find `settings.css/js` + `assets/vendor/lucide.min.js` for THAT page (`lib:370-375`); every host plugin must therefore ship the CSS/JS/Lucide files at the same relative paths (`lib/wbcom-settings/settings.css`, `assets/vendor/lucide.min.js`) even when its own class copy is not the one running.
- Upgrading: no tooling. Edit one copy, bump `const VERSION` and the `wbcom_settings_register()` literal, hand-copy to siblings, hand-regenerate `settings-rtl.css`. There is no source repo path in the reference (comment at `lib:26` "analysed in its own repo" per phpstan.neon.dist:18 - a lib repo exists but is not named). **Action for the rewrite: pull the newest copy from the most recently released Wbcom Woo plugin (check `Wbcom_Settings_Page::VERSION`), do not copy 1.0.3 blindly; also copy its `settings-rtl.css` from the same source.** Bump `loader.php` docblock too.

## 2. The admin wrapper: exact mechanics

### 2.1 Registration chain
1. `register_activation` irrelevant. At `plugins_loaded -999`: `Wbcom_Settings_Page` class available.
2. `init` prio 1: `Woo_..._Admin::boot_settings_page()` (admin:175-198) calls
```php
Wbcom_Settings_Page::boot( array(
  'prefix'     => 'wcmp',                       // hook prefix; required
  'slug'       => 'woo-custom-myaccount-page',  // menu slug / ?page= ; required
  'assets_url' => WCMP_PLUGIN_URL,              // plugin root URL; required
  'version'    => WOO_CUSTOM_MY_ACCOUNT_PAGE_VERSION, // cache-bust for own assets
  'icon'       => 'circle-user-round',          // Lucide icon name, brand tile + hub card
  'labels'     => array( 'menu_title','brand','subtitle','nav_label', 'pro_badge' ), // CALLER translates
  // optional: 'legacy_slugs' => array( 'old-page-slug' )  -> redirected on admin_menu prio 1 (lib:278-292)
) );
add_filter( 'wcmp_settings_nav_groups', ... );   // lib:324
add_action( 'wcmp_settings_tab_content', ... );  // lib:542
```
   `boot()` is idempotent per slug and wires 4 hooks once (first page only): `admin_menu` 20 `register_pages`, `admin_menu` 1 `redirect_legacy_slugs`, `admin_enqueue_scripts` `enqueue`, `in_admin_header` 1 `quieten_foreign_notices` (`lib:112-117`).
3. `admin_menu` prio 5: plugin adds the top-level menu **only if `$GLOBALS['admin_page_hooks']['wbcomplugins']` is empty**: `add_menu_page( 'WB Plugins','WB Plugins','manage_options','wbcomplugins', ['Wbcom_Settings_Page','render_welcome'], 'dashicons-lightbulb', 59 )` (admin:154-168). `render_welcome()` builds a card grid by reading `$GLOBALS['submenu']['wbcomplugins']`, so it lists every Wbcom plugin whether or not it uses the lib; helper slugs (`wbcom-plugins-page` etc.) are filtered via `wbcom_hub_wrapper_helper_slugs` (`lib:166-202`).
4. `admin_menu` prio 20: `add_submenu_page( 'wbcomplugins', menu_title, menu_title, 'manage_options', $slug, ['Wbcom_Settings_Page','render'] )` (`lib:125-136`). Resulting screen base: `wb-plugins_page_<slug>`. Parent screen: `toplevel_page_wbcomplugins`.
5. First submenu entry becomes the parent's default landing; the hub "Welcome" page is the parent's own callback.

### 2.2 Page shell (render()) - `lib:451-551`
```
<div class="wrap wbcom-admin">
  <h1 class="screen-reader-text">{brand}</h1>
  <hr class="wp-header-end">                       <- REQUIRED anchor for core notice relocation (lib:472-486)
  settings_errors();                               <- called by the shell, after the marker (lib:488)
  <div class="wbcom-settings-wrap">                <- CSS grid 240px | 1fr (settings.css)
    <nav class="wbcom-settings-sidebar" aria-label=...>
       brand tile (Lucide icon from boot['icon']) + brand + subtitle
       foreach nav group: label + <a class="wbcom-settings-nav-item [is-active]" data-section=tab_id aria-current href=?page=slug&tab=id>
           <i data-lucide=icon></i><span>title</span>[<span class="wbcom-pro-badge">]
    <div class="wbcom-settings-content">
       foreach tab id (ALL tabs rendered into DOM at once): <div class="wbcom-settings-section [is-active]" id="section-{tab}">
            <div class="wbcom-settings-body"> do_action( '{prefix}_settings_tab_content', $tab_id ) </div>
```
- Active tab = `?tab=` validated against registered ids else first (lib:466-468). Tab URL helper `Wbcom_Settings_Page::tab_url($slug,$tab)` (`:564`).
- **Every tab's renderer runs on every page load** (lib:528-546). Heavy queries (the pincode data tab with 20k rows!) must be lazy: render a shell/placeholder and fetch via REST, or only run when `$tab === $_GET['tab']`. WCMP gets away with it because its tabs are cheap. This is a big-site-checklist item for the pincode plugin.
- Tab renderers emit only bare content; chrome via `Wbcom_Settings_Page::card_open( $title, $desc )` / `card_close()` (`lib:578-598`) -> `<section class="wbcom-card"><div class="wbcom-card__head"><p class="wbcom-card__title">..<p class="wbcom-card__desc"></div><div class="wbcom-card__body">`. Each tab = vertical stack of cards (matches ux-foundation rulebook:58).
- Nav array shape (admin:207-241): `array( 'main' => array( 'label'=>'My Account', 'items'=>array( 'wcmp-overview'=>array('title'=>..,'icon'=>'gauge','pro'=>bool) ) ), 'help' => array(...) )`; tab ids carry the plugin prefix (`wcmp-overview`).
- Reference tabs: overview, endpoints, general, style, faq -> `switch ( $tab )` in `render_settings_tab()` (admin:249-273). Overview = status badges + counts + quick-action buttons + support links (admin:280-376), as CLAUDE.md:207-215 demands ("land on an Overview, not a form").
- Header: no visible page header / version pill (gap vs CLAUDE.md:213 and Part 6 rule "every page starts with `{prefix}-page-header`"). The hub page does have `.wbcom-page-header` (`lib:207`).
- Dependency state: none on-screen beyond the runtime notice; add a "WooCommerce missing" empty state if you register the page before the Woo check (reference registers only after the Woo guard, so the page vanishes with WC).

### 2.3 Settings registration, save, sanitize
- **Settings API, form POST to `options.php`, one option + one option group per tab/concern** (not REST, not AJAX): `register_setting( 'wcmp_general_settings', 'wcmp_general_settings', [$this,'wcmp_general_settings_callback'] )` etc. on `admin_init` (admin:520-524; hooked includes:137). Forms live inside the tab renderer: `<form method="post" action="options.php"><?php settings_fields('wcmp_general_settings'); ?> ...fields named wcmp_general_settings[key]... <div class="wbcom-save-bar"><?php submit_button(..., 'wbcom-btn wbcom-btn--primary','submit',false); ?></div></form>` (admin:395-460, 489-506; endpoints partial `admin/partials/wcmp-endpoints-settings.php:18-103`).
- `register_setting` is called with the 3rd arg as a bare callable (legacy signature, no `type`/`default`/`show_in_rest`/`sanitize_callback` array). Use the array form in 1.6.0 (`'type'=>'object'|'array', 'sanitize_callback'=>..., 'default'=>..., 'show_in_rest'=>false`) so defaults are declared once and `get_option` falls back to them.
- Sanitizers (admin:761-822, 855-955): per-key allowlists (`'yes'/'no'` checkbox normalisation because unchecked boxes send nothing; `sanitize_title`, `sanitize_hex_color`, `sanitize_key`, type allowlists). Note menu_style / sidebar_position use `sanitize_text_field` without an enum allowlist (admin:~782-789) - the pincode rewrite should `in_array( ..., [...], true )` every enum.
- Save notice: core's `options.php` redirects back with `settings-updated=true`; on a custom admin page core does not print it automatically, so the **shell prints `settings_errors()` itself** (`lib:488`) and styles `.notice.settings-error` as a success card (`settings.css:31-75`, a rule that also `display:none`s any other `.notice:not(.wbcom-notice):not(.settings-error)`). Your sanitizers can add errors with `add_settings_error()` and they will show.
- Tab survives save: `settings.js:48-62` rewrites the hidden `_wp_http_referer` of each form inside a section to `...&tab=<section>` on submit, so the redirect lands on the same tab. Works because each tab form is wrapped in `.wbcom-settings-section`. JS tab switching is progressive enhancement over real `?tab=` links (`settings.js:36-46`), `history.replaceState`, then `lucide.createIcons()`.
- Side effects on save via `update_option_<name>` actions (includes:140,146): mirror slugs to WC core options (admin:739-756) and schedule a 60 s transient-flag rewrite flush (admin:957-967).

### 2.4 CSS token system, dark mode, RTL, mobile, icons
- Admin tokens (`settings.css:21-32`): `.wbcom-admin { --wbcom-border:#e2e8f0; --wbcom-surface:#fff; --wbcom-muted:#646970; --wbcom-text:#1e1e1e; --wbcom-accent:var(--wp-admin-theme-color,#2271b1); --wbcom-accent-strong:var(--wp-admin-theme-color-darker-10,#135e96); --wbcom-success:#16a34a; --wbcom-sidebar-bg:#f6f7f7; }` - accent follows the user's admin colour scheme with fallbacks, as CLAUDE.md:157-174 prescribes. Other colours are literals (and ~gradient `#6366f1,#8b5cf6` on line 175; `#fff` text on the logo tile).
- **Dark mode: absent** in the admin shell and in the plugin's admin CSS. Frontend has a documented bridge (below). If admin dark mode is required for 1.6.0, add a scoped `@media (prefers-color-scheme: dark) { .wbcom-admin { --wbcom-surface:...; ... } }` in the plugin's own `admin/assets/css/...admin.css` (loads after, same specificity) rather than editing the lib. WP admin itself has no dark mode, so a dark panel inside a light admin chrome is wrong - decide before building (ux-foundation `dark-mode-and-rtl.md`).
- Frontend bridge (`public/assets/css/woo-custom-my-account-page-public.css:24-66`): `:root { --wcmp-accent: var(--bx-color-accent, var(--reign-accent-color, var(--wp--preset--color--primary, var(--wp--preset--color--accent, #157dfd)))); --wcmp-bg/--wcmp-surface/--wcmp-text/--wcmp-muted/--wcmp-border ...; --wcmp-radius:8px; --wcmp-tap:40px }` then `@media (prefers-color-scheme: dark){ :root:not([data-bx-mode]){...literal dark values...} }`; components read only `--wcmp-*`. Follows CLAUDE.md:98-149. (Note: the chain is only valid for Woo storefront output; for pincode widgets on product pages reuse the same table with prefix `--wcpc-*`.)

- **Reference**: no custom tables, no CPTs, no repositories/models (CLAUDE.md:338; manifest `tables:[]`).
