## 2. Data stores

### 2.1 Custom table `{prefix}pincode_checker` (one table)
Fresh-install schema (`R/includes/class-woo-pincode-checker-activator.php:47-65`, dbDelta, InnoDB default):
```
id               int(11) NOT NULL AUTO_INCREMENT
pincode          varchar(20) NOT NULL
city             varchar(100) NOT NULL
state            varchar(100) NOT NULL
delivery_days    int(11) DEFAULT 1
shipping_amount  decimal(10,2) DEFAULT 0.00
case_on_delivery tinyint(1) DEFAULT 0
cod_amount       decimal(10,2) DEFAULT 0.00
created_at       datetime DEFAULT CURRENT_TIMESTAMP
updated_at       datetime DEFAULT CURRENT_TIMESTAMP        (no ON UPDATE -> never changes)
category_rules   TEXT NULL
latitude         DECIMAL(10,8) NULL
longitude        DECIMAL(11,8) NULL
PRIMARY KEY (id), UNIQUE KEY unique_pincode (pincode), KEY idx_city (city), KEY idx_state (state)
```
Upgrade path (`wpc_update_table_structure` main:419-454 / `wpc_ensure_table_indexes` 461-490) adds `created_at/updated_at` as `TIMESTAMP` (ON UPDATE on updated_at), and indexes `unique_pincode`, `idx_pincode_search(pincode)` (redundant duplicate of the unique key), `idx_city_state(city,state)`, `idx_delivery_days`. It does NOT add `idx_city`/`idx_state`.
Third schema variant in the Manual Fix page SQL (main:654-672): `TINYINT UNSIGNED delivery_days`, `TIMESTAMP`, `idx_created_at`, no lat/long/category_rules. => 3 divergent schemas depending on install path. `created_at`/`shipping_amount` sorts have no index anywhere on fresh installs; no index on latitude/longitude.
Semantics: `pincode` is a free string (3-10 alnum + single inner spaces, `validate_pincode` is copy-pasted in public.php:65, form.php:165, admin.php:125); not normalised (case/space) before lookup: "ab1 2cd" != "AB1 2CD" under a case-insensitive collation they match but `LIKE`/cache keys (md5 of raw string) don't.

## 6. Scale (store with 30k+ pincodes)

Frontend lookup path is fine: `WHERE pincode=%s` hits `unique_pincode`. Problems:
1. `check_table_exists()` (`SHOW TABLES LIKE`) is executed repeatedly per request: on `init` for every front request (form.php:700, through `wpc_set_wc_billing_and_shipping_zipcode`), 2-3x per product page (form.php:299, 335/391 via safe_db_* each re-checking), plus `wpc_check_update_mysql_db` (2 queries) every request. And if the table is "missing" it runs DDL on a front-end request (form.php:75).
2. Nearby by distance (nearby.php:265-326): loads ALL geocoded rows into PHP and runs Haversine per row for every unserviceable lookup, no bounding-box pre-filter, no index on lat/long; also `check_geocoding_available` runs 2 full COUNTs (`latitude IS NOT NULL` unindexed) on every unserviceable check (nearby.php:431-445). With 30k rows that is a 30k-row fetch per guest request, rate-limited only by 10 req/min/IP.
3. The same unserviceable path can call Nominatim synchronously from a public guest request (`find_nearby_by_distance` -> `geocode_pincode_nominatim`, nearby.php:271): up to 1s `sleep` + 10s timeout inside a nopriv AJAX call; a single abusive client ties up PHP workers; also violates Nominatim usage policy for production traffic (1 req/s global, heavy use discouraged).
4. Prefix fallback (nearby.php:336-392) uses `LIKE 'xxxx%'` (index-friendly) but with a `NOT IN (SELECT ...)` subquery.
5. Admin list: search branch has NO `LIMIT/OFFSET` (listing.php:293: pagination only applied when `s` is empty) -> `SELECT *` of up to the whole table for a 3-char search; `LIKE '%term%'` on pincode+city+state = full scan (no fulltext, no index usable). COUNT(*) executed 2-3x per list render (prepare_items + `extra_tablenav` top) - fine on InnoDB but wasteful. No filter by state/COD/geocoded, no per-column index for sorts on `created_at`/`shipping_amount`.
6. CSV import (admin.php:1333-1466): sequential `SELECT COUNT(*)` + `INSERT` per row, one HTTP request, `set_time_limit(300)`, 5MB cap (~150k rows possible) -> will time out behind nginx/Cloudflare (60-100s) with partial import and no resume; a pattern row (`110***`) inserts up to 10,000 rows with the same N+1 and no 1000 cap. No transaction, no batching (`INSERT ... VALUES (...),(...)` / `INSERT IGNORE` / `ON DUPLICATE KEY` would remove the SELECT).
7. Bulk add (bulk-add.php:76-139): same N+1; hard cap 1000 (bulk-add.php:55) contradicts the 10,000 cap in the pattern handler and the help text; with auto-geocode each pincode costs >=1s + up to 10s -> 1000 rows = 17-170 minutes in one request, `set_time_limit(300)` only applied if >100.
8. Geocode batch (admin.php:2076 -> nearby.php:475-544): 50 pincodes/request, each >=1s (+10s when Nominatim slow) -> 50-550s per AJAX call; PHP/proxy timeouts hit first. Selecting rows uses `latitude IS NULL OR (latitude=0 AND longitude=0)` unindexed.
9. `apply_global_rules_to_all_pincodes` (category-rules.php:207-246) = per-row UPDATE loop (unused).
10. `get_terms` for all product categories on General/Category tabs (no limit) - fine under normal catalogs.
11. `wp_cache_flush()` (full site object-cache flush) on every `activate()` call (activator.php:105), and `activate()` is invoked from runtime self-heal paths.
12. TRUNCATE for "delete all" is O(1) but has no confirm of count and no backup.
13. Frontend assets/inline CSS/JS load on every page type (public.php:181-241; form.php:640).

## 7. Security

Good: capability checks (`manage_options`) + nonces on all admin handlers; prepared statements almost everywhere; output mostly escaped; cookies httponly+secure-aware.
Findings:
- S1 Raw SQL, unprepared: `find_nearby_by_distance` interpolates `$pincode` into `AND pincode != '{$pincode}'` (nearby.php:288). Input is validated upstream (alnum+space only) so not exploitable today, but a public-reachable raw string interpolation; any future caller with unvalidated input = SQLi. Also unprepared `COUNT` queries nearby.php:435-436, 456-457, 536, category-rules.php:224, admin.php:1717 (TRUNCATE, table name only), main:591-593 (table name only).
- S2 `$wpdb->prepare()` with no placeholder (activator.php:121-123) -> `_doing_it_wrong` notice on each activation/self-heal.
- S3 Nonce hygiene: single shared generic nonce action `ajax-nonce` for both public AJAX endpoints; `wpc-pincode-submit` reused for add, edit and CSV upload and the nonce is read from a POST key named after the nonce itself (admin.php:906, 1265); list bulk-delete nonce missing from markup (see 1/23); `wbcom_addons_cards` has nonce only, no capability (wbcom-admin-settings.php:37-44).
- S4 Public AJAX order of checks: `check_table_exists()` (may run DDL) before nonce (form.php:470); checkout AJAX rate-limits before nonce (public.php:350). Rate limit relies on `REMOTE_ADDR` only (shared across all visitors behind a CDN/proxy without real-IP restoration => whole store throttled to 10 req/min) and non-atomic get/set transient (race), key schemes differ between the two classes.
- S5 Guest nonce embedded via `wp_localize_script` on every page => stale on cached pages; not a vuln but functional failure.
- S6 Unescaped output: JS `displaySuggestions` builds HTML from raw `pincode/city/state` (public.js:~480; dead path); admin AJAX row HTML `__()` and `$pincode['delivery_days']` concatenated unescaped (dead); `wpc_display_pincode_field` prints `esc_html`'d city then re-escapes (fine); `$nearby['distance_km']` unescaped numeric (form.php:612); inline `style` attributes everywhere (CSP-hostile).
- S7 Data integrity / privacy: overwrites `shipping_postcode` user meta (form.php:419, 574); third-party calls to BigDataCloud from the browser (dead) and Nominatim from the server with the visitor's entered postal code and site URL in the User-Agent (nearby.php:58) - undisclosed external service, no opt-in, no privacy-policy text.
- S8 `$_FILES['import']['tmp_name']` passed through `sanitize_text_field` (admin.php:1290) (can corrupt paths); MIME check allows `text/plain`; ok otherwise. CSV values stored with `sanitize_text_field` only, no length cap -> DB errors on `varchar(100)` (non-strict mode truncation).
- S9 `uninstall.php` leaves personal-free but persistent data/cron (not security, but hygiene).
- S10 `wp_redirect` (not `wp_safe_redirect`) in listing.php:499,522 (URL derived from `remove_query_arg` of current URL; low risk).
- S11 Admin screen notices all suppressed (admin.php:359-368) hides security/update notices from other plugins on those pages.

## 9. The 7 reported bugs

### 9a. Bulk Add by pattern/range slow, no progress, can time out (worse with auto-geocode) - CONFIRMED
- Synchronous, one HTTP request, server-rendered, no AJAX/progress: `R/admin/partials/woo-pincode-bulk-add.php:20-163`.
- Per pincode: `SELECT COUNT(*) ... WHERE pincode=%s` then `$wpdb->insert` (lines 78-83, 132) = 2 queries/row, no batching.
- `set_time_limit(300)` only when >100 rows (64-66); hard cap `1000` rows (55-61) although pattern handler allows 10,000 (`pattern-handler.php:29`) and the help text promises "Maximum 10,000 pincodes per pattern" (bulk-add.php:193).
- Auto-geocode multiplies it: `geocode_pincode_with_details` per row (bulk-add.php:98) does `sleep()` to enforce 1 req/s (nearby.php:97-105) + `wp_remote_get` timeout 10s (nearby.php:124); 1000 rows >= ~17 min, far above any gateway timeout; result message only after completion; a 504 leaves a partial insert with no report.
- Geocode failures are not retried and just insert with NULL coords.
- No cache invalidation after insert.

### 9b. "Import Bulk Post/Zip codes" link wrong slug; bulk delete has no callback (admin.php ~761-763) - PARTLY FIXED, PARTLY STILL BROKEN

Page slug is correct (registered admin.php:432-439) BUT only exists when WooCommerce is loaded under the shared `wbcomplugins` parent; `.old` used `woo-pincode-checker` (the wrong slug). Separate still-broken slug: Plugins list "Settings" link `page=woo-pincode-checker` (main:754).
- Bulk delete: STILL BROKEN. `<a class="add-new-h2 wpc-bulk-delete">` has no href (admin.php:836-838). Its handler lives in `admin/js/woo-pincode-checker-admin.js:65-110` which is enqueued only when screen id contains `pincode-checker-for-woocommerce` or `wbcomplugins`, or `?page=` equals `pincode-checker-for-woocommerce`/`woo-pincode-checker` (admin.php:296-326). The list page screen id is `toplevel_page_pincode_lists`, so the script (and `wpc_admin_ajax.nonce`) never loads there; click does nothing. ### 9c. "Add to cart behaviour for unavailable pincodes" conflicts with "Make pincode field required": button hides on typing - NOT REPRODUCED as stated; real conflict CONFIRMED
- No handler hides the button on typing: the only input handlers (public.js:44-52) validate format/show suggestions (`handleInputChange` ~395-410); `.single_add_to_cart_button` is touched only at public.js:114/116 (load, `handleAddToCartBehavior` 104-120), 218 (success), 245/247 (error), 297-304 (`showPincodeForm`).
- Real conflicts: (1) one setting `add_to_cart_option` (label "for unavailable pincodes", admin-display.php:113) is also reused as the "pincode required, not yet verified" behaviour (public.js:109-117, 292-301). (2) Settings UI shows "Hide" selected for an unsaved value, but the stored default is '' (activator.php:206); with '' the error branch does nothing (public.js:243-248 matches neither value) while the required-mode load branch `.hide()`s -> inconsistent behaviour until the admin saves. ### 9d. Pincode input disappears from product pages after saving Category Rules - CONFIRMED as a historic root cause; MITIGATED in 1.6.0 with a residual path
- Root cause (before 9db75e4): `wpc_general_settings_sanitize` started with `$sanitized = array()` and the Category Rules form posts ONLY `wpc_general_settings[global_category_rules]`, so saving it replaced the whole option and dropped `pincode_position`. `wpc_single_product_button_position()` then returned '' (general-functions.php:55-65) and `define_public_hooks` attached nothing (class-woo-pincode-checker.php:246-259) => no form.
- 1.6.0 mitigation: sanitizer now seeds from the stored option (admin.php:547-550) and guesses the tab (555-556).
- Residual: Category Rules form omits all unchecked rows and disabled `days` inputs (category-rules-display.php:81-101), so with ZERO rules enabled the POST has no `wpc_general_settings` key at all -> `$input` is null -> `$is_category_rules_tab` false -> the General branch runs and RESETS `date_display`, `pincode_field`, `cod_display` to '' (admin.php:559-564) and the saved rules can never be cleared (the `global_category_rules = []` branch at 652-655 is unreachable for the "clear all" case). Also `pincode_position` stays blank forever for installs that predate the key and never opened General (no default fallback in the getter).

### 9e. General and Category Rules tabs share `wpc_general_settings` and overwrite each other on save - CONFIRMED (design flaw), symptom mitigated
- Both tabs `register_setting('wpc_general_settings','wpc_general_settings', ...)` (admin.php:704, 739) and both forms use `settings_fields('wpc_general_settings')` (admin-display.php:47, category-rules-display.php:31). Separation is by key-sniffing in one sanitizer (admin.php:555-559) which is fragile: any new field/tab or empty POST changes the branch (see 9d residual). The General tab's `categories_for_shipping` resets when the `categories_for_shipping[]` select is empty only if `$is_general_tab` (admin.php:616-621), which depends on other keys being present.
- Correct fix (for the rewrite): separate options (`wpc_general_settings`, `wpc_category_rules`) or per-tab sanitizers keyed by a hidden `_tab` field; avoid whole-array replacement.

### 9f. Geocoding gets stuck: no result, no fallback, no OpenStreetMap status indicator - CONFIRMED
- Any non-200, WP_Error, or empty result is logged only to `error_log` and returns null (nearby.php:64-74, 79-86); in `geocode_batch` that null is turned into a PERMANENT failure marker (lat/long 0.001,0.001, nearby.php:511-519) - so HTTP 429/503/timeouts (transient) permanently mark good pincodes as failed. The `latitude=0 AND longitude=0` retry predicate (nearby.php:481-484) does not match the 0.001 marker, so they are never retried; stats count them as "geocoded" (`latitude IS NOT NULL`, nearby.php:436,457) so the UI says 100% complete and "Nearby suggestions are active" while those rows have fake coordinates and are included in Haversine searches.
- No fallback provider, no city/state-based fallback, country hard-coded `IN` (nearby.php:47, 110): non-Indian stores (the sample CSV is US ZIPs) get no results; only `postalcode` query is used.
- No status indicator: no health check of Nominatim, no per-error reporting (UI only shows "Skipped N failed"), no last-error/last-success timestamp, no pause/resume, no rate-limit awareness (Retry-After ignored).
- "Stuck" mechanics: batch = 50 rows x (>=1s sleep + up to 10s timeout) = 50-550s in one admin-ajax request (nearby.php:475-544), no `set_time_limit`, JS has no `timeout`/error-retry (geocoding-display.php:168-218); progress math is per batch (`processed/(processed+remaining)`, line 180-181) so the bar jumps/stays low; on network error it just re-enables the button; closing the tab stops the "background" process (copy at line 118 says "runs in background"). Rate limit uses a transient with 5s TTL and `sleep` (nearby.php:35-42), racy across concurrent requests (public guests + admin batch).
- Public requests can trigger geocoding too (nearby.php:271, 9/scale).

### 9g. `fgetcsv()` `$escape` deprecation importing the sample CSV - REJECTED for live code (fixed), still present in dead code
- Reproduced on PHP 8.5.10: calling `fgetcsv($h)` emits "Deprecated: fgetcsv(): the $escape parameter must be provided..." (also `fputcsv`), explicit `fgetcsv($h,0,',','"','\\')` is silent. Live import path passes the escape explicitly since 6900e31: `R/admin/class-woo-pincode-checker-admin.php:1188, 1196, 1340, 1345`.
- Remaining occurrences are all in the never-loaded `R/admin/class-woo-pincode-checker-import-export.php` (fgetcsv 300, 332, 447, 452, 467; fputcsv 184, 198, 583).
- Sample file quirks (not deprecations): `sample-data/sample-pincodes.csv` has 10 columns (3 trailing empty), a trailing space on row 2, US ZIP data with Indian sample defaults elsewhere, header names differ from the dead exporter ("Delivery Days" vs `delivery_days`). Import header row is skipped blindly (no header validation, no BOM handling in the live path).

## 11. Verdict (keep vs throw away)

Keep (behaviour/algorithms, not code): the pincode->record lookup model (unique pincode, city/state, delivery_days, shipping_amount, COD flag + COD fee, optional lat/long), the delivery-date estimate (+N days with clamp), the per-product hide metabox and category-exclude concept, fee-based shipping/COD surcharge by pincode, the pattern/range expander with its 10k safety cap (add alphanumeric support, fix `*` vs `?` semantics, don't treat every `-` as a range), the two-tier "nearby" idea (Haversine when coordinates exist, prefix match as fallback) but with a bounding-box SQL pre-filter and without on-request external geocoding, the 1 req/s Nominatim batching idea (but as a resumable background job with retry/backoff and honest status), the cookie-remembered pincode with DB re-validation, rate limiting of guest AJAX (with proxy-aware IP and atomic counters), the HTML/JS "check -> message -> change" UX and the add-to-cart hide/disable/required behaviour (re-specified as one state machine). Keep the CSV column contract (pincode, city, state, delivery_days, shipping_amount, cash_on_delivery, cod_amount) and the sample-data idea. Throw away: the boilerplate loader/i18n/deactivator layers, the shared wbcom admin wrapper and its cross-sell pages and CDN Font Awesome, the self-healing DDL on front-end requests and per-request SHOW TABLES, the single mega-option shared by unrelated tabs, the key-sniffing sanitizer, the global-category-rules tab as built (no runtime effect) and the unused per-pincode `category_rules` JSON column design (replace with a real rules table or drop), the dead import/export class, AJAX search/sort scaffold, autocomplete/geolocation/monitor JS, the throwaway-`WC_Customer` postcode code, destructive `shipping_postcode` user-meta writes, the shipping-suppression filters (integrate as a proper WC shipping method / Store API aware fee instead), the phantom docs and `FUNCTIONALITY_AUDIT.md`, `.old`, and the 3 divergent schemas. The rewrite must additionally add what is missing: server-side add-to-cart and checkout enforcement (classic + Blocks via Store API), COD gateway gating, REST + WP-CLI + export, chunked/queued import and bulk add (Action Scheduler) with progress, indexed and paginated admin list with filters, uninstall cleanup, WC cart/checkout-blocks and PHP 8.1-8.5 declarations, one text domain/slug, and a tested migration from the 1.5.x table/options (keep table name `{prefix}pincode_checker` and option `wpc_general_settings` readable for upgrades).
